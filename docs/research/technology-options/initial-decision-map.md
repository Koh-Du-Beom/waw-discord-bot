# 초기 기술 결정 지도와 조사 순서

- 상태: Research plan
- 작성일: 2026-07-20
- 연결 문서: `docs/research/technical-constraints.md`
- 제한: 후보군과 검증 질문만 정의하며 추천, 최종 선택 또는 ADR 승인을 하지 않는다.


```text
제품 범위·운영 목표·보존/RPO/RTO (D-01)
  ├─ 외부 데이터 가능성: Discord/Riot/KBO/요약 (D-02)
  │    └─ 이벤트·데이터 흐름과 도메인 경계 (D-03)
  │          ├─ 언어·런타임·Discord SDK (D-04)
  │          ├─ 영구 저장소·마이그레이션 (D-05)
  │          └─ 요약 처리·모델 공급 방식 (D-06)
  ├─ 인증·인가·세션·감사 위협 모델 (D-07)
  └─ 배포 경계와 봇-웹 통신 (D-08)
       ├─ 봇 지속 호스트와 단일 실행 (D-09)
       ├─ 웹 프레임워크·대시보드 배포 (D-10)
       ├─ 비밀·로그·모니터링 (D-11)
       └─ 백업·복구·롤백 (D-12)

D-02, D-03, D-05, D-07, D-08의 불확실성
  └─ 승인된 최소 Spike 후보 (D-13)

비교 결과와 Spike 증거
  └─ Proposed ADR 묶음과 승인 순서 (D-14, 이 작업의 범위 밖)
```

이 구조의 핵심 경로는 `D-01 → D-02 → D-03 → D-08`이다. 외부 API가 실제 기능을 제공하는지와 시스템 경계를 먼저 확인하지 않으면 런타임, 저장소 또는 호스팅 비교 기준이 바뀔 수 있다.

## 평가 기준 공통 틀

각 기술 조사 문서는 다음 기준을 필요한 만큼 수치화한다.

1. 요구사항 충족 여부: 필수 요구를 충족하지 못하면 비용과 친숙도와 무관하게 제외한다.
2. 공식 지원과 유지보수: 공식 문서, API 안정성, 지원 종료와 보안 대응을 확인한다.
3. 보안·개인정보: 권한 경계, 비밀, 원문 비저장과 데이터 처리 조건을 확인한다.
4. 신뢰성·복구: 장애 모드, 멱등성, 백업, 복구와 롤백을 확인한다.
5. 운영 부담: 배포, 관측, 온콜, 업데이트와 공급자 종속성을 비교한다.
6. 검증 가능성: 로컬 테스트와 폐기 가능한 Spike로 핵심 가설을 재현할 수 있어야 한다.
7. 총비용: 예상 사용량과 소유자 비용 상한을 기준으로 고정·변동 비용을 분리한다.
8. 단순성: 요구를 만족하는 범위에서 구성요소, 신규 의존성, 사용자 정의 인프라가 가장 적은 후보를 우선 비교한다.

## 증거 기반 조사 순서

### 0. 소유자 입력과 측정 기준 확정

- `OWN-001`~`OWN-009`를 검토해 MVP 순서, 예상 부하, 비용, 보존, RPO/RTO와 정책 값을 수집한다.
- 산출물: 기술 독립적인 평가 가중치와 통과/실패 기준.
- 종료 조건: 수치가 없으면 범위를 명시한 복수 시나리오로 비교하기로 합의한다.

### 1. 외부 플랫폼 가능성 조사

- Discord Gateway/Go Live 관측, 메시지 조회 범위와 OAuth 권한을 공식 자료로 확인한다.
- Riot 계정 연결, 솔로 랭크 게임 시작·종료 감지의 공식 지원과 정책을 확인한다.
- KBO 일정·결과·순위·팀 정보를 합법적이고 안정적으로 제공할 수 있는 1차/공식 공급 경로를 확인한다.
- 요약 공급자의 데이터 보존, 컨텍스트 한계, 처리량과 비용 단위를 확인한다.
- 이유: 이 단계에서 불가능하거나 제한된 기능은 후속 아키텍처의 전제를 바꾼다.

### 2. 데이터 흐름과 위협 모델 작성

- 명령, 원문 메시지의 일시 처리, Riot/Discord 이벤트, 설정 변경, 감사와 백업 흐름을 그린다.
- 각 신뢰 경계, 저장 여부, 보존, 행위자 권한, 재시도와 중복 키를 표시한다.
- 이유: 기술을 고르기 전에 `PRI-001`, `DAT-003`, `SEC-001~009`의 충족 방식을 비교 가능하게 만든다.

### 3. 배포 경계 연구

- 정책에 명시된 네 형태를 동일한 부하·RPO/RTO·비용 가정으로 비교한다.
- 웹/봇 분리 시 API, 큐, 공유 저장소와 이벤트 방식을 공개 면적과 장애 모드 중심으로 비교한다.
- 이유: 런타임과 제품별 호스팅 비교 전에 필요한 지속성·네트워크·보안 조건을 확정한다.

### 4. 저장소와 백업·복구 공동 연구

- 트랜잭션, 무결성, 멱등성, 마이그레이션과 내보내기를 먼저 평가한다.
- 같은 후보에서 암호화 백업, 분리 보관, 빈 환경 복구, RPO/RTO와 비용을 함께 비교한다.
- 이유: DB 기능만 따로 고르면 복구 요구를 뒤늦게 별도 시스템으로 보완할 위험이 있다.

### 5. 런타임·Discord SDK와 봇 호스트 연구

- D-02의 실제 API 필요와 D-03/D-08의 경계를 기준으로 공식 SDK 지원, 재연결, 테스트성과 지속 실행을 비교한다.
- 익숙함이나 인기만으로 점수화하지 않는다.

### 6. 인증·웹·운영 도구 연구

- Discord 서버/역할 재검증과 세션 경계를 먼저 정한 후 웹 프레임워크와 배포 후보를 비교한다.
- 이어서 비밀 관리, 감사/운영 로그, 메트릭과 경보 후보를 배포 경계에 맞춰 평가한다.

### 7. 요약 처리 전략 연구

- 소유자가 정한 최대 범위와 비용/지연 목표로 계층적 처리, 실패 계약과 원문 비영구 처리를 비교한다.
- 합성 데이터로 완전성 측정 방법을 먼저 정의하며 실제 Discord 원문을 벤치마크 자료로 저장하지 않는다.

### 8. 불확실성별 Spike 제안

- 문서 증거로 결론 낼 수 없는 항목만 한 가설씩 분리한다.
- 우선 후보: Go Live 관측 가능성, 단일 봇 실행, 장문 요약 완전성, 분리 웹-봇 인증, 중복 이벤트, 빈 환경 복구.
- 각 Spike는 별도 승인 전 실행하지 않고 제품 코드나 운영 의존성으로 승격하지 않는다.

### 9. Proposed ADR 계획

- 근거가 모이면 배포 경계, 데이터·복구, 인증, 런타임/SDK, 외부 공급자 등 되돌리기 단위로 ADR을 분리한다.
- 모든 ADR은 `Proposed`로 시작하고 소유자 승인 전 `Accepted`로 바꾸지 않는다.
- 이 단계는 현재 작업의 종료점 이후에 별도 요청으로 수행한다.

## 조사 문서별 완료 조건

- 연결 요구사항 ID와 평가 기준이 있다.
- 최소 두 개의 현실적 대안과 가장 강한 대안이 포함된다.
- 공식 또는 1차 출처의 확인일과 링크가 있다.
- 확인 사실, 추론, 가정과 미확인 사항이 구분된다.
- 비용 수치는 사용량·지역·시점과 함께 기록된다.
- 필요한 Spike와 결정을 뒤집을 조건이 있다.
- 임시 추천이 있더라도 프로젝트 결정이나 Accepted ADR로 표현하지 않는다.

## 현재 하지 않는 일

- 구체적인 제품·언어·프레임워크·공급자 추천 또는 순위 확정
- 의존성 설치, 계정 생성, 배포와 외부 시스템 변경
- Spike 실행
- ADR 생성 또는 승인
- 구현 계획과 제품 코드 작성
